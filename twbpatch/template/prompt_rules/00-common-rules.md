# 共通ルール

## リネーム後名称の決め方
- フィールド、フォルダ、階層の名前には日本語の業務用語を使う。フィールド名を英語のままにしない（例: Order Date → 注文日）。
- データソース全体で同じ意味のフィールド名を重複させない。既存の名前とぶつかる場合は意味が分かる修飾語を足す（例: Region → 地域、Region (People) → 地域（担当者））。
- 内部用の列（Sheet、Table Name など、業務で使わないもの）は元の名前のままにする。
- 判断材料が足りない項目は意味を推測して確定せず、元の名前を維持する。

## フォルダの決め方
- 名前は「01_売上指標」のように、2 桁の番号 + アンダースコア + 日本語名にする。
- 番号は、業務で見る順（重要な指標 → 補助的な情報 → 管理用）に振る。
- ディメンションとメジャーは別のフォルダに分ける。
- 1 フォルダは 3〜10 個を目安にする。1 個しかないフォルダは作らない。
- 内部用の列はフォルダに入れず、空欄にする。

## 階層の決め方
- ドリルダウンに意味がある組み合わせにだけ付ける。上から下へ「粗い → 細かい」の順に並べる（例: カテゴリ → サブカテゴリ → 商品名、国 → 都道府県 → 市区町村）。
- 階層に入れる行には同じ階層名を書き、入れない行は空欄にする。
- 1 つの階層には 2 つ以上のフィールドが必要。1 つだけなら空欄にする。
- 同じ階層のフィールドは同じフォルダに置く。
- 階層名は、どのフィールドの表示名とも違う名前にする（例: 商品階層、地理階層）。
- 日付フィールドで階層を作らない。Tableau が年・四半期・月を自動で用意する。
- 1 つのフィールドを 2 つの階層に入れない。

## データソース構造の読み方
データソース構造は、次のインデントで表す。

データソース
　フォルダ/
　　階層/
　　　フィールド
　　階層に属さないフィールド

- インデントが深い項目は直前の浅い項目に属し、同じ深さの項目は同じ親に属する。
- フォルダと階層の末尾の `/` は構造を読むための記号。出力するフォルダ名・階層名には付けない。

## 分類ファイルの使い方
- 顧客・商品などの分類ファイルには、その分類固有の対応辞書とデータソース構造を書く。共通の命名・フォルダ・階層ルールはこのファイルだけに置く。
- 複数の分類ファイルを選んだ場合は、各フィールドに該当する適用対象と条件だけを参照する。
- 同じ入力項目に複数の候補があり、条件から判別できない場合は元の名前を維持し、フォルダ・階層は空欄にする。
