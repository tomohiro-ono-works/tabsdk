# タスク: 設定を画面で行う仕組み（HTML 出力 → 設定ファイル）

- 起票日: 2026-09-05
- 更新日: 2026-09-06（**範囲を見直した。当初の「範囲 a」から拡大**）
- 対象: `docs/backlog.md` の J-1 / J-2 / J-3 / J-4

## 目的

ダッシュボードを組む前に、データソースのフィールドを調べて Python コードへ手で書き写す作業が
発生している。フィールドが数十個あると現実的でない。
**HTML を出力し、画面で設定して設定ファイルを吐かせる**ことでこれを置き換える。

## 範囲の見直し（2026-09-06）

当初は「範囲 a（表示名とフォルダ割り当てのみ）」で起票した。
その後、画面仕様として次の 4 つが要望として出た。

| # | 画面 | 内容 |
|---|---|---|
| 1 | 全体 | （内容未定） |
| 2 | データソース / リネーム・フォルダ | Excel のようなセル状の表。**コピペ可能** |
| 3 | データソース / 計算フィールド | Excel のようなセル状の表。**コピペ可能** |
| 4 | ダッシュボード | ヘッダー編集 + ボディ（縦段組 → 横配置 → エリア → グラフ／フィルター選択 → グラフパラメータ → アクション設定） |

これは当初の範囲 a を超え、2 と 3 が範囲 b、4 が範囲 c〜d に当たる。

## 二段構えにする

**データソース側とダッシュボード側で、着手できる状態が違う。**

| 段 | 画面 | 出力先の Python 側 | 着手 |
|---|---|---|---|
| 第 1 段 | データソース設定（上表の 2・3） | `apply_field_config()` が既にある | **今すぐ可** |
| 第 2 段 | ダッシュボード設定（上表の 4） | `build_report()`。**形が固まっていない** | 土台 3 件の後 |

### 第 2 段を後回しにする理由

画面が吐く設定ファイルの形は、それを受け取る Python 側の引数の形で決まる。
ダッシュボード側は受け手が 3 箇所とも未確定で、**先に画面を作ると設定ファイルの形が
後から変わり、画面ごと作り直しになる。**

| 未確定なもの | 課題 | 状態 | 画面のどこに効くか |
|---|---|---|---|
| `build_report()` の `struct` 形式 | K-1 | 未着手。コンテナ名に「フィルタ」が含まれるかで動作が変わる（`connected_dashboard.py:798`） | 縦段組・横配置・エリア |
| グラフ種類ごとの引数ルール | H-10 | 未確定 | グラフパラメータ選択 |
| ダッシュボードアクション | H-1 | 未実装 | アクション設定 |

ヘッダー編集だけは `build_report()` の `header_height` / `header_background_color` /
`header_font_color` が既にあるが、単独で切り出す価値は小さいので第 2 段にまとめる。

## 共通の制約

- **外部依存を増やさない。** 現在の依存は `lxml` と `PyYAML` のみ。
  HTML は文字列として生成し、CSS と JavaScript はインラインに埋め込む。
  テンプレートエンジンも CDN も使わない（オフラインで開けること）。
  **表計算ライブラリ（Handsontable 等）は使えない。セル状の表は自前で書く。**
- **サーバを立てない。** ブラウザからのダウンロードで設定ファイルを受け渡す。
- 出力した HTML は単体で完結し、他のファイルを参照しない。

# 第 1 段: データソース設定画面

## 既にある部品

| 部品 | 場所 | 役割 |
|---|---|---|
| `TwbWorkbook.export_json()` | `twbpatch/workbook.py` | ワークブックの内容を辞書で取り出す |
| `serialize_workbook()` | `twbpatch/serialization.py:110` | 上記の実体。フィールドは名前・型・役割・計算式・フォルダまで含む |
| `TwbDatasource.apply_field_config()` | `twbpatch/connected.py` | 表示名とフォルダを一括適用する |
| `TwbWorkbook.apply_field_config()` | `twbpatch/workbook.py` | ワークブック単位の同処理 |

**読み出しと書き戻しは実装済み。作るのは真ん中だけ** ……ただし計算フィールドは別（後述）。

## 決めるべきこと

実装より先に決着が必要なもの。**決めないと着手できない。**

### D1. 出力の単位と API 名

- ワークブック全体を 1 つの HTML にするか、データソースごとに分けるか
- 複数データソースがある場合の扱い（タブ切り替えを想定）
- `TwbWorkbook.export_html(path)` でよいか。`TwbDatasource` にも置くか
- 仕様 §3.3 の命名規則に反しないか（`export_*` は `export_json()` の前例あり）

### D2. 「全体」タブに何を置くか

要望では見出しだけで内容が空。候補:

- ワークブック名・データソース一覧・ワークシート／ダッシュボード一覧（読み取り専用の目次）
- 出力ファイル名など、画面全体に効く設定
- **何も置かない**（タブ自体を作らない）

### D3. セル状の表をどこまで作り込むか

「Excel のような」「コピペ可能」の解像度を決める。外部ライブラリが使えないので、
作り込むほど自前の JavaScript が増える。

| 段階 | 内容 |
|---|---|
| 最小 | `contenteditable` のセル + 貼り付け時に TSV を分解して複数行・複数列へ展開 |
| 中 | 上 + 範囲選択・コピー（選択範囲を TSV でクリップボードへ）・矢印キー移動 |
| 大 | 上 + 行の挿入／削除、元に戻す、列の並べ替え |

**貼り付けの分解（TSV → 複数セル）は最小段階でも必須。** これが無いと
「Excel からコピペする」という要望を満たさない。

### D4. 計算フィールドの設定ファイル形式

**現行の YAML は表示名とフォルダしか表現できない**（`データソース名 → フォルダ名 → {元名: 表示名}`）。
計算フィールドには式・データ型・役割が要るので、**形式の拡張（J-3）が第 1 段の前提になる。**

- 既存の `ec_site_fields.yaml` と後方互換を保つか、新形式に切り替えるか
- 保つ場合、計算フィールドをどのキーの下にぶら下げるか
- 出力順を安定させる（現行は記述順に依存している）
- 書き戻す Python 側 API を新設するか、`apply_field_config()` を拡張するか

### D5. 画面から出るのは 1 ファイルか 2 ファイルか

リネーム・フォルダと計算フィールドを 1 つの YAML にまとめるか、別々に落とすか。
D4 の形式と一体で決める。
